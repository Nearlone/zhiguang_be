# DeepSeek 对话补全与流式输出

> 整理来源：[DeepSeek 对话补全 API](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)

## 请求结构

对话补全接口接收 `messages` 数组。每条消息包含角色和内容，常见角色包括 `system`、`user`、`assistant` 和 `tool`。System 消息用于声明全局规则，User 消息表示用户请求，Assistant 消息保存模型历史回复，Tool 消息用于回传工具执行结果。

API 本身不等于长期记忆。应用进行多轮对话时，需要在每次请求中重新携带必要的历史消息，或者由服务端从会话存储中读取并组装。历史越长，输入 Token 和调用成本通常越高。

## 生成参数

`max_tokens` 限制本次最多生成多少输出 Token，不包含已经发送的输入 Token，但输入与输出总长度仍受模型上下文窗口限制。值过小可能使回答因 `finish_reason=length` 被截断，值过大则扩大最坏成本和响应时间。

`temperature` 控制输出随机性。较低值会使结果更集中、稳定，适合知识库问答；较高值增加多样性，更适合创意任务。官方接口还提供 `top_p`，通常调整 temperature 或 top_p 其中一个即可，不建议同时大幅修改两者。

## SSE 流式响应

当 `stream=true` 时，服务端通过 Server-Sent Events 持续发送增量内容，最后以结束标记终止。流式传输不会减少模型总生成时间，但能缩短用户看到首个字符的等待时间。

应用不能假设每个流式响应都包含文本。最后的响应块可能只携带 usage 等元数据。正确做法是先读取响应元数据，再跳过没有文本的块，而不是因为正文为空就忽略整条响应。

客户端中断连接时，后端应处理取消信号并记录状态。已经消耗的模型 Token 不一定能够撤销，因此需要区分成功、异常和用户取消。

## Token usage

非流式响应通常在 `usage` 中返回 `prompt_tokens`、`completion_tokens` 和 `total_tokens`。开启相应流式选项后，最后一个额外数据块也可以携带整次请求的 Token 统计。

服务商返回的 usage 比本地字符估算更准确。工程上可以在调用前使用估算做预算和参数校验，调用后优先记录服务商 usage；若服务商没有返回，再使用估算值作为降级数据，并标记来源。

## JSON 与工具调用安全

启用 JSON 输出时，Prompt 仍要明确要求模型生成 JSON，否则模型可能持续输出空白直到达到限制。即使启用了 JSON 或严格模式，业务端也必须校验字段、类型和权限。

工具调用中的参数由模型生成，可能缺字段、格式错误或出现未定义参数。调用真实函数前要做 Schema 校验、资源权限校验和敏感操作确认，不能把模型输出直接当作可信命令执行。
