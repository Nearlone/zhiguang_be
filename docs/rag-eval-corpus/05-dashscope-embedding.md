# DashScope 文本向量化

> 整理来源：[阿里云百炼向量化](https://help.aliyun.com/zh/model-studio/embedding?disableWebsiteRedirect=true)

## Embedding 的输入输出

Embedding 模型接收文本，输出固定维度的数值向量。向量不是自然语言答案，而是文本语义的数学表示，适合语义检索、聚类、推荐和分类。Chat 模型则接收消息并生成文本，两者不能互相替代。

RAG 索引阶段把文章切片转换成文档向量，查询阶段把用户问题转换成查询向量，再计算相似度。两阶段必须使用兼容的模型、维度和向量处理方式。

## 模型与维度

`text-embedding-v3` 默认输出 1024 维，也支持 768、512、256、128 和 64 等可选维度。较高维度通常保留更多语义信息，但会增加存储、网络和检索计算成本。降低维度可以节省资源，但可能损失召回精度。

模型还存在单批输入数量和最大 Token 等限制。批量写入时，应同时考虑接口允许的文本条数、总 Token、请求体大小和超时，而不能只按数据库记录数量分批。

## query 与 document

部分 DashScope 接口支持通过 `text_type` 区分查询文本和文档文本：

- `query` 用于用户查询，表示更短、更有方向性的检索需求；
- `document` 用于知识库正文，表示包含更多信息的长文本。

短查询匹配长文档时，明确区分两种角色有助于优化检索效果。是否启用该参数取决于实际调用接口和 SDK，使用 OpenAI 兼容接口时要核对它是否暴露相同能力。

## 稠密向量与稀疏向量

稠密向量擅长语义理解和同义表达，但不保证字段名或 SKU 等精确词一定命中。稀疏向量更关注关键词，计算和存储模式也不同。`dense&sparse` 同时返回两类表示，适合构建混合检索，但索引结构和融合逻辑更复杂。

知光当前可以用 BM25 承担关键词通道，用稠密 Embedding 承担语义通道，再通过 RRF 融合排名。这样不要求向量服务同时输出稀疏向量。

## API Key 与错误处理

DashScope API Key 应通过环境变量注入，例如 `DASHSCOPE_API_KEY`，不能写进 Git 或返回给前端。Key 失效、余额不足、限流、超时和输入过长都可能导致向量生成失败。

生产代码应记录服务商、模型、批次和错误类型，但日志不能包含完整 Key 或大段敏感正文。发布流程如果依赖向量可用，应把失败状态明确返回前端，并提供可重试机制。
