# Elasticsearch 混合检索

> 整理来源：[Elastic Hybrid Search](https://www.elastic.co/docs/solutions/search/hybrid-search)
>
> 本文为测试语料整理稿，重点描述全文检索和向量检索的互补关系。

## 为什么需要两条检索通道

全文检索关注词项是否匹配，向量检索关注文本在语义空间中是否接近。两者解决的问题不同：BM25 擅长参数名、错误码、产品型号、数字和专有名词；向量检索擅长同义改写、自然语言描述和字面不同但含义相近的问题。

例如问题中出现 `rank_window_size`，包含该精确字段名的片段通常应被优先找到。若用户问“怎样避免一种检索方式垄断候选结果”，文章写的是“平衡词法相关性与语义相关性”，向量检索更可能建立两者之间的联系。

## BM25 的作用

BM25 根据查询词在文档中的出现情况、词的稀有程度以及文档长度计算相关性。常见词的区分度较低，少见术语的区分度较高。它不需要调用 Embedding 模型，结果容易解释，适合精确术语召回。

BM25 的不足是对词汇差异敏感。查询和正文表达不同，即使含义一致，也可能得不到理想排名。中文分词、大小写、符号和字段映射也会影响最终结果。

## 向量检索的作用

向量检索先使用同一个 Embedding 模型把查询和文档表示成向量，再使用余弦相似度、点积或其他距离函数寻找邻近结果。它可以识别同义词和上下文关系，但不保证精确字段名一定排在前面。

向量检索还依赖模型版本、向量维度、索引算法和查询参数。如果文档向量与查询向量来自不同模型或不同维度，检索结果将不可比较，甚至无法写入索引。

## 混合检索流程

典型混合检索先让全文检索和向量检索分别生成候选列表，再把两路排名融合成一个列表。融合后应按文档或切片唯一标识去重，限制最终上下文数量，并保留来源信息。

```text
用户问题
  ├─ BM25：精确术语候选
  └─ KNN：语义相近候选
          ↓
      融合、去重、截断
          ↓
      结构化 RAG 上下文
```

在单篇知文问答中，两路查询都应先使用 `postId` 过滤当前文章。混合检索不是把全站文章混在一起，而是在当前文章的多个切片之间同时使用两种相关性信号。

## 融合时的风险

BM25 分数和向量相似度通常不在同一个量纲，直接相加会引入偏差。简单把 BM25 列表放在前面、向量列表放在后面，也可能因为最终数量限制而完全丢掉向量结果。

工程上可以使用 RRF 按排名融合，或者使用经过评测校准的加权归一化。无论采用哪种方法，都应记录两路命中数量、融合后切片 ID、检索耗时和最终回答质量。
