# Elasticsearch 稠密向量字段

> 整理来源：[Elasticsearch Dense Vector Field](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/dense-vector/)

## dense_vector 保存什么

`dense_vector` 字段保存由一组数值组成的稠密向量，主要用于 KNN 相似度检索。它与普通文本字段不同，不用于聚合或常规排序，并且一个字段只能保存一个向量值。

向量可以使用浮点数组等形式写入。映射中的 `dims` 表示向量维度，必须与 Embedding 模型输出一致。例如索引声明为 1024 维，就不能写入 768 维向量。更换 Embedding 模型或维度后，通常需要创建新索引或重建全部向量。

## KNN 检索

文档入库时保存正文、向量和元数据。查询时先把用户问题转换成同模型、同维度的向量，再执行近邻检索。为了让单篇文章问答不受其他文章影响，可以在 KNN 查询阶段增加 `postId` 元数据过滤。

近似近邻索引通过牺牲少量精度换取更低延迟。工程上通常先扩大候选窗口，再对候选做融合或精排。只增加最终 `topK` 会同时扩大 Prompt，可能提高 Token 成本并引入无关证据。

## 向量量化

量化用于降低向量搜索的内存占用。常见策略包括 `int8`、`int4` 和二进制量化。`int8` 用一个字节表示每一维，内存占用显著下降；`int4` 进一步压缩，但要求维度数量满足相应限制；二进制量化把每一维压缩到一位，节省更多内存，同时带来更大的精度损失。

量化并不意味着原始向量一定完全消失。某些索引方案仍保留原始浮点向量，用于重排、重建或精度恢复，因此磁盘占用和内存占用需要分别评估。

## 过采样与重排

量化向量的近似结果可以通过 oversampling 扩大候选，再使用原始向量重新计算分数。这样会增加查询计算量，但可能找回因量化误差而排名靠后的正确结果。

RAG 场景可以采用“两阶段检索”：第一阶段低成本召回较多候选，第二阶段用原始相似度、RRF 或语义重排选出少量上下文。最终仍要控制交给模型的片段数量。

## 生产注意事项

索引设计至少要固定以下契约：Embedding 模型名、模型版本、向量维度、相似度函数、索引版本和元数据结构。修改任何一项，都应判断旧向量是否需要迁移。

写入失败时不能把文章标记为索引成功。批量写入还要记录批次、总切片数和失败原因，避免出现数据库显示 READY、向量库实际缺片的状态不一致。
