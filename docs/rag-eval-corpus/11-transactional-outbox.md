# Transactional Outbox 模式

> 整理来源：[AWS Transactional Outbox Pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

## 双写问题

一个业务操作经常需要同时更新数据库并发送消息。例如文章发布时，既要把 `know_posts.status` 改为 published，又要通知异步消费者创建搜索和 RAG 索引。这两个动作属于不同系统，普通本地事务无法同时保证它们成功。

如果数据库提交成功但消息发送失败，下游永远不知道文章已发布；如果消息先发送成功而数据库回滚，下游会处理一条不存在的业务变更。这就是双写不一致。

## Outbox 的核心做法

Transactional Outbox 在业务数据库中增加事件表。业务数据修改和 Outbox 事件写入使用同一个本地事务：

```text
BEGIN
  UPDATE know_posts ...
  INSERT INTO outbox_events ...
COMMIT
```

任何一条 SQL 失败都会一起回滚。事务提交后，独立发布器轮询 Outbox 表，或者 CDC 组件监听变更，再把事件发送到 Kafka 等消息系统。

这种方案保证的是业务状态与“待发送事件”原子一致，而不是保证消息绝不重复。发布器可能已经发送成功，却在更新 Outbox 状态前崩溃，恢复后会再次发送同一事件。

## 幂等消费

消费者必须把重复消息视为正常情况。每条事件应具有稳定的 `eventId`，消费者可以通过去重表、唯一约束或业务版本号判断是否已经处理。

只有记录日志而不做幂等不能阻止重复写入。例如“文章索引已存在就跳过”需要比较内容指纹或索引版本，而不是只判断 Elasticsearch 中是否存在任意旧向量。

## 顺序问题

同一业务实体可能连续产生发布、更新和删除事件。若事件乱序，旧更新可能覆盖新版本，或者删除后又写回旧索引。Outbox 可以保存创建时间和序列号，但跨并发发布器时仍需设计分区键和版本校验。

Kafka 中可以把实体 ID 作为消息 key，使同一实体进入同一分区。消费者还可以比较事件版本，只处理比当前版本新的事件。

## 失败与重试

Outbox 表通常记录状态、重试次数、下一次执行时间和最后错误。发布失败应使用指数退避，超过阈值后进入人工检查或死信流程。长期成功记录需要归档或清理，避免表无限增长。

业务事务中不能吞掉 Outbox 插入失败。如果更新文章成功后捕获事件写入异常并继续提交，双写问题会重新出现。发布接口应回滚并明确返回失败。

## Outbox 与 CDC

轮询实现简单，但会增加数据库查询和发送延迟。CDC 读取数据库日志，减少轮询压力，但需要维护 Canal、Debezium 等组件以及位点、重放和监控。

两种方式都不能取消消费者幂等。Outbox 解决事件不遗漏，CDC 解决事件如何可靠离开数据库，消费者幂等解决重复到达后的业务一致性。
