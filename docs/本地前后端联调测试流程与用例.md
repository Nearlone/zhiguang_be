# 知光项目本地前后端联调测试流程与用例

> 适用环境：`zhiguang_be` + `zhiguang_fe` 本地开发环境  
> 前端地址：`http://localhost:5173`  
> 后端地址：`http://localhost:8080`  
> 前端通过 Vite 将 `/api` 代理到后端，因此页面测试时不需要配置 `VITE_API_BASE_URL`。

## 1. 测试目标

本轮测试分为两个层级：

1. **P0 基础链路**：不依赖 OSS 和大模型，验证环境、认证、JWT、资料、Feed、点赞收藏、关注等功能。
2. **P1 完整链路**：配置 OSS、DeepSeek、DashScope 后，验证发布、搜索索引、AI 摘要、向量索引和 RAG。

建议先完成全部 P0 用例，再进入 P1。否则出现错误时，很难判断问题来自基础业务、对象存储还是模型服务。

## 5. P0 认证链路测试

### TC-AUTH-01：匿名访问公开 Feed

操作：未登录访问首页。

预期：

- `GET /api/v1/knowposts/feed?page=1&size=20` 返回 `200`。
- 没有数据时返回 `items: []`，页面应展示空状态而不是报错。
- 请求不需要 `Authorization`。

### TC-AUTH-02：未登录访问受保护接口

操作：清除 Local Storage，访问个人中心或直接请求：

```bash
curl -i http://localhost:8080/api/v1/auth/me
```

预期：返回 `401 Unauthorized`，不应返回用户数据。

### TC-AUTH-03：用户 A 发送注册验证码

操作：

1. 前端进入 `/register`。
2. 输入 `13800000001`。
3. 点击发送验证码。
4. 在后端日志查找：

```text
Send verification code scene=REGISTER identifier=13800000001 code=xxxxxx
```

也可以从 Redis 查询：

```bash
docker exec zhiguang-redis redis-cli \
  HGET auth:code:REGISTER:13800000001 code
```

预期：

- `POST /api/v1/auth/send-code` 返回 `200`。
- Redis 中生成 `auth:code:REGISTER:13800000001`。
- Key 有约 5 分钟 TTL。

检查 TTL：

```bash
docker exec zhiguang-redis redis-cli \
  TTL auth:code:REGISTER:13800000001
```

### TC-AUTH-04：验证码错误

操作：使用错误验证码注册。

预期：

- 注册失败。
- 不创建用户。
- Redis 中 `attempts` 增加。
- 连续错误达到上限后，后续错误验证码被拒绝。

### TC-AUTH-05：密码不符合规则

分别测试：

- `12345678`：没有字母。
- `abcdefgh`：没有数字。
- `Test123`：不足 8 位。

预期：注册失败，并返回密码策略相关提示。

### TC-AUTH-06：正常注册并自动登录

操作：

1. 输入正确验证码。
2. 密码填写 `Test123456`。
3. 勾选同意协议。
4. 点击“立即注册”。

预期：

- 注册成功并自动登录。
- 响应包含 `user` 和 `token`。
- Local Storage 出现 `zhiguang_auth_tokens`。
- 其中包含 `accessToken` 和 `refreshToken`。
- `GET /api/v1/auth/me` 返回当前用户资料。
- 注册验证码 Key 在成功校验后被删除。

### TC-AUTH-07：重复注册

操作：再次使用用户 A 手机号发送 `REGISTER` 验证码或注册。

预期：被拒绝，提示账号已存在；数据库不出现重复账号。

### TC-AUTH-08：验证码登录

操作：

1. 退出登录。
2. 进入 `/login`。
3. 为用户 A 发送 `LOGIN` 验证码。
4. 从日志或 Redis 获取验证码。
5. 完成登录。

Redis Key：

```bash
docker exec zhiguang-redis redis-cli \
  HGET auth:code:LOGIN:13800000001 code
```

预期：登录成功，Local Storage 写入新的双令牌。

### TC-AUTH-09：Access Token 保护

操作：

1. 登录后打开个人中心。
2. 在 Network 中检查 `/api/v1/auth/me`。
3. 手动删除 `Authorization` 后重放请求。

预期：

- 携带有效 Access Token 时返回 `200`。
- 不带 Token、Token 被篡改或过期时返回 `401`。

### TC-AUTH-10：刷新令牌轮换

从 Local Storage 复制 Refresh Token：

```bash
curl -X POST http://localhost:8080/api/v1/auth/token/refresh \
  -H 'Content-Type: application/json' \
  -d '{"refreshToken":"<旧Refresh Token>"}'
```

预期：

- 返回新的 Access Token 和 Refresh Token。
- 旧 Refresh Token 从 Redis 白名单撤销。
- 再次使用旧 Refresh Token 刷新应失败。

### TC-AUTH-11：登出

操作：点击页面退出登录。

预期：

- `POST /api/v1/auth/logout` 返回 `204`。
- Local Storage 中认证信息被清除。
- 被登出的 Refresh Token 不能再次刷新。
- 已签发的 Access Token 在过期前可能仍可使用，这是当前无状态 JWT 的正常行为。

## 13. 故障定位顺序

页面操作失败时，按以下顺序排查：

1. 浏览器 Console 是否有前端异常。
2. Network 中请求是否发出，URL 是否为 `/api/...`。
3. HTTP 状态码是 `400、401、403、404、500` 中哪一种。
4. 请求是否携带正确的 Bearer Access Token。
5. 后端控制台是否出现业务异常或堆栈。
6. `docker compose ps` 中依赖是否健康。
7. Redis Key、MySQL 数据、Kafka 消费和 ES 文档是否符合预期。
8. 最后再检查 OSS、DeepSeek、DashScope 等外部服务。

常用命令：

```bash
# 容器状态
docker compose ps

# 容器日志
docker compose logs --tail=100 mysql redis kafka elasticsearch canal

# Redis Key
docker exec zhiguang-redis redis-cli --scan --pattern 'auth:*'

# Kafka Topic
docker exec zhiguang-kafka \
  /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:29092 --list

# Elasticsearch 索引
curl http://localhost:9200/_cat/indices?v

# 后端健康状态
curl http://localhost:8080/actuator/health
```
