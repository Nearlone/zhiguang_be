### Q6：知文发布链路怎么走？

**推荐回答：**

知文发布链路不是一个大接口，而是分阶段完成。

1. 前端调用创建草稿接口，后端生成一个知文 ID。
2. 前端根据这个 ID 请求 OSS 预签名上传 URL。
3. 后端校验当前 JWT 用户是否拥有这个草稿，然后生成限定 objectKey 和过期时间的 PUT URL。
4. 前端用这个 URL 直接把图片或正文上传到 OSS。
5. 正文上传成功后，前端调用 content/confirm，把 objectKey、etag、size、sha256 回传后端。
6. 前端再调用 PATCH 元数据接口，保存标题、标签、图片 URL、可见性、摘要。
7. 最后调用 publish 接口，把状态从 draft 改成 published。
8. 发布后首页 Feed、详情页、搜索和 RAG 才能基于这篇内容工作。

**项目接口：**

```text
POST /api/v1/knowposts/drafts
POST /api/v1/storage/presign
POST /api/v1/knowposts/{id}/content/confirm
PATCH /api/v1/knowposts/{id}
POST /api/v1/knowposts/{id}/publish
```

**追问：为什么要创建草稿？**

因为上传文件前需要有一个业务 ID，后端可以根据 postId 生成 objectKey，并校验这个 postId 属于当前用户，避免用户随意上传到其他目录。

### Q7：OSS 预签名直传是什么？为什么不用后端转发上传？

**推荐回答：**

OSS 预签名直传是指后端使用自己的 AccessKey 生成一个短期有效的上传 URL，前端拿这个 URL 直接把文件 PUT 到 OSS。

不用后端转发上传主要是为了减少后端压力。图片和正文文件如果先传到后端，再由后端上传 OSS，会占用后端带宽和连接资源；直传 OSS 可以让文件流量直接走对象存储，后端只负责鉴权、生成 objectKey 和保存元数据。

同时也不能把 Bucket 设置成公共写，因为公共写风险太大，任何人都能上传垃圾文件或恶意文件。预签名 URL 可以做到 Bucket 不开放公共写，但用户仍然能在短时间内上传到后端指定位置。

**追问：预签名 URL 有什么安全点？**

- URL 有过期时间。
- objectKey 由后端生成。
- 后端校验 postId 归属。
- 只允许特定 HTTP Method，比如 PUT。
- 可以绑定 Content-Type。

**追问：还有什么可以加强？**

- 限制文件大小。
- 限制 Content-Type 白名单。
- 上传后后端 HEAD Object 校验。
- 图片内容安全审核。
- 对生成 presign URL 做限流。

### Q8：你遇到过 OSS CORS 问题吗？怎么解决？

**推荐回答：**

遇到过。前端页面运行在 `http://localhost:5173`，OSS 地址是另一个域名。浏览器对跨域 PUT 请求会先发送 OPTIONS 预检请求，如果 OSS Bucket 没有配置允许这个 Origin、Method 和 Header，浏览器会直接拦截。

当时浏览器报错类似：

```text
No 'Access-Control-Allow-Origin' header is present
```

排查时我看到后端创建草稿和生成 presign URL 都成功，说明失败点不在后端，而在浏览器直传 OSS。解决方式是在阿里云 OSS Bucket 的 CORS 规则中配置：

```text
AllowedOrigin: http://localhost:5173
AllowedMethod: GET, HEAD, PUT, POST
AllowedHeader: *
ExposeHeader: ETag
```

**追问：为什么要暴露 ETag？**

因为前端上传成功后需要读取 OSS 响应头里的 ETag，再回传给后端确认上传结果。浏览器默认不能读取所有响应头，所以需要配置 ExposeHeader。

### Q9：上传成功但图片不显示，可能是什么原因？

**推荐回答：**

上传成功和能够公开读取是两个权限面。预签名 PUT URL 只代表这个 URL 可以上传文件，但上传后的裸 URL 是否能被浏览器 GET，要看 Bucket 或对象有没有读权限。

我联调时遇到过：OSS 中已经有文件，但前端图片不显示。原因是前端把 `presign.putUrl.split("?")[0]` 当作图片地址，这个地址如果没有公共读权限，浏览器 GET 时就会失败。

解决方式有两类：

1. 本地测试可以设置 Bucket 公共读，但不能公共写。
2. 更安全的生产方案是 Bucket private，读取时后端生成预签名 GET URL，或者通过后端鉴权代理读取。

### Q10：AI 摘要链路怎么实现？

**推荐回答：**

AI 摘要是在创建知文页面中触发的。用户填写正文后点击 AI 摘要开关，前端先判断用户是否登录、正文是否为空。然后调用：

```text
POST /api/v1/knowposts/description/suggest
```

这个接口需要 Bearer Token。后端 Controller 接收正文后，调用 `KnowPostDescriptionService`。服务中通过 Spring AI 的 ChatClient 构造 system prompt 和 user prompt，调用 DeepSeek 的 `deepseek-chat` 模型。

模型返回结果后，后端会做后处理，比如去换行、合并空格、去掉多余引号和标点，并按 code point 截断到 50 字以内。前端拿到 description 后填入摘要输入框，发布时再作为 `description` 保存到数据库。

**追问：为什么不是发布时自动生成？**

因为摘要生成有成本，也可能失败。由用户主动点击生成，可以让用户确认和修改摘要，避免发布流程被模型调用强依赖卡住。

### Q11：Prompt 怎么设计？

**推荐回答：**

项目里将 Prompt 分成 system 和 user 两部分。

system prompt 用来约束模型角色和输出格式，例如：

```text
你是中文文案编辑，请基于正文生成中文描述，简洁有吸引力，不超过 50 个汉字，不输出解释。
```

user prompt 放正文和具体任务：

```text
正文如下：...
请直接给出不超过 50 字的中文描述。
```

这样做的好处是稳定规则和用户输入分离，结构清晰，也更方便后续维护。

**追问：只靠 Prompt 能保证 50 字吗？**

不能。Prompt 是软约束，大模型可能不严格遵守。所以后端还会做 hard limit，把输出截断到 50 字以内。

### Q12：Spring AI ChatClient 在项目里怎么用？

**推荐回答：**

项目通过 Spring AI 的 ChatClient 调用 DeepSeek。核心流程是：

```java
chatClient
    .prompt()
    .system(system)
    .user(user)
    .options(DeepSeekChatOptions.builder()
        .model("deepseek-chat")
        .temperature(0.8)
        .maxTokens(120)
        .build())
    .call()
    .content();
```

`system` 和 `user` 组成模型输入，`DeepSeekChatOptions` 设置模型名、temperature 和最大输出 token。返回后调用 `.content()` 获取文本结果。

**追问：temperature 是什么？**

temperature 控制随机性。越低越稳定，越高越发散。摘要场景既要自然一点，又不能太离谱，所以项目里设置为 0.8。

**追问：maxTokens 为什么设置 120？**

摘要只需要 50 字以内，120 个 token 基本足够，避免生成太长内容造成成本浪费。

### Q13：大模型调用失败怎么办？

**推荐回答：**

项目里用 try-catch 包住大模型调用。如果调用失败，会抛业务异常，前端展示错误提示。

本地联调时我发现摘要链路没有明显日志，因为它不走数据库，也没有 MyBatis SQL。后来我给摘要服务补了日志，记录输入长度、输入预览、模型原始输出、后处理结果和失败异常，方便判断请求是否真的打到后端和模型。

**追问：生产中日志要注意什么？**

- 不要打印 API Key。
- 不要把超长正文完整打印到 INFO。
- 可以打印长度和截断预览。
- 错误详情写后端日志，前端返回友好提示。
- 对调用失败做降级，比如允许用户手动填写摘要。

### Q14：RAG 问答链路怎么走？

**推荐回答：**

RAG 是检索增强生成。项目里做的是单篇知文 RAG 问答。

链路是：

1. 发布或提问时读取知文正文。
2. 将正文按 Markdown 结构和长度切分成 chunk。
3. 调用 Embedding 模型把每个 chunk 转成向量。
4. 将向量和 metadata 写入 Elasticsearch 向量索引。
5. 用户在文章详情页提问。
6. 系统把问题也转成向量。
7. 在向量库中召回相关 chunk。
8. 将召回内容和问题拼进 Prompt。
9. 调用 DeepSeek 生成答案。
10. 通过 SSE 流式返回给前端。

**追问：为什么是单篇文章 RAG？**

因为用户是在某篇知文详情页提问，问题通常围绕当前文章内容。单篇 RAG 可以减少无关内容干扰，也更容易控制回答范围。

---

### Q15：RAG 和普通问答有什么区别？

**推荐回答：**

普通问答主要依赖模型自身参数中的知识，可能出现知识过时、上下文缺失和幻觉。

RAG 会先从外部知识库检索相关内容，再把检索结果作为上下文提供给模型，让模型基于材料回答。

简单说：

```text
普通问答：问题 -> 大模型
RAG：问题 -> 检索相关资料 -> 拼接上下文 -> 大模型
```

RAG 的优势是可以接入私有知识、降低幻觉、增强答案可追溯性。

---

### Q16：为什么要做文档切分？

**推荐回答：**

如果整篇文章作为一个向量，粒度太粗，检索时很难定位具体内容；如果切得太碎，又会丢失上下文语义。

切分 chunk 的目的是在检索精度和语义完整性之间平衡。通常会按标题、段落或 Markdown 结构切分，并设置最大长度和 overlap。

**追问：chunk size 怎么选？**

不是越大越好，也不是越小越好。大 chunk 上下文完整但召回不精准，小 chunk 精准但可能语义不完整。可以先按经验设置，比如 800 字符、100 overlap，再根据问答效果调。

---

### Q17：Embedding 是什么？

**推荐回答：**

Embedding 是把文本转换成高维向量，使语义相近的文本在向量空间中距离更近。

在 RAG 中，文档 chunk 会被转成向量存入向量库；用户问题也会转成向量，然后通过相似度检索找到最相关的 chunk。

项目里使用 embedding 模型生成向量，再存入 Elasticsearch vector store。

**追问：为什么维度要一致？**

因为向量相似度计算要求两个向量长度一致。如果文档向量是 1536 维，问题向量也必须是 1536 维，否则无法计算相似度。

---

### Q18：为什么使用 Elasticsearch 做向量检索？

**推荐回答：**

Elasticsearch 本身适合搜索场景，支持关键词检索，也支持 dense vector 和 kNN 向量检索。知光项目既有搜索模块，也有 RAG 向量检索，因此用 Elasticsearch 可以统一搜索和向量检索基础设施。

当然，向量库不只有 Elasticsearch，也可以用 Milvus、pgvector、Qdrant 等。项目里选择 ES 更多是为了和现有搜索能力结合，降低系统复杂度。

**追问：Elasticsearch 相比专门向量库有什么不足？**

专门向量库在超大规模向量检索、索引压缩、召回性能和向量管理上可能更专业。ES 的优势是搜索生态成熟、和文本检索结合方便。

### Q19：SSE 是什么？为什么 RAG 回答用 SSE？

**推荐回答：**

SSE 是 Server-Sent Events，基于 HTTP 的服务端单向推送机制，响应类型是：

```text
text/event-stream
```

大模型回答可能比较长，如果等完整回答生成完再返回，用户等待时间会很长。SSE 可以边生成边返回，让前端逐字或逐段展示，体验更接近打字机效果。

相比 WebSocket，SSE 更简单，适合服务端向客户端持续推送文本的场景。

**追问：SSE 和 WebSocket 区别？**

SSE 是单向推送，WebSocket 是双向通信。大模型回答通常是用户发起请求后服务端持续返回内容，单向就足够，所以 SSE 更轻量。

---

### Q20：JWT 鉴权在项目里怎么做？

**推荐回答：**

项目使用 Spring Security OAuth2 Resource Server 来校验 Bearer JWT。

请求带上：

```text
Authorization: Bearer accessToken
```

Spring Security 过滤链会解析 JWT，校验签名和过期时间。校验通过后，Controller 可以通过：

```java
@AuthenticationPrincipal Jwt jwt
```

拿到当前 JWT，再从里面提取用户 ID。

**追问：JWT 有哪几部分？**

JWT 是三段：

```text
Header.Payload.Signature
```

Header 存算法，Payload 存 claim，比如 sub、exp、jti、uid，Signature 用来防止篡改。

---

### Q21：Access Token 和 Refresh Token 的区别？

**推荐回答：**

Access Token 用来访问业务接口，过期时间短。Refresh Token 用来换取新的 Access Token，过期时间较长。

这样做是为了平衡安全和体验：

- Access Token 泄露后影响时间较短。
- Refresh Token 可以让用户不用频繁登录。
- Refresh Token 放 Redis 白名单，可以支持服务端撤销。

项目中登出或重置密码时，可以删除 Redis 中对应的 Refresh Token jti，让旧 Refresh Token 失效。

---

### Q22：为什么验证码和 Refresh Token 都适合 Redis TTL？

**推荐回答：**

它们都是有明确过期时间的数据。

验证码只在几分钟内有效，适合 Redis 自动过期，也方便记录错误次数、发送频率和每日次数限制。

Refresh Token 的白名单记录也有生命周期，TTL 可以和 token 的 exp 保持一致。到期自动清理，登出或重置密码时可以主动删除。

**项目 key 示例：**

```text
auth:code:REGISTER:13800000000
auth:rt:100:tokenJti
```

---

### Q23：Feed/详情缓存怎么理解？

**推荐回答：**

Feed 和详情是典型读多写少场景，适合缓存。项目里可以理解为：

```text
Caffeine 本地缓存 -> Redis 分布式缓存 -> MySQL
```

本地缓存速度最快，Redis 支持多实例共享，MySQL 是最终数据源。

更新或发布内容后，需要清理相关缓存，避免用户看到旧数据。项目里也有缓存失效和延迟双删的设计思路。

**追问：缓存一致性怎么保证？**

缓存一致性很难做到强一致，通常是：

- 更新数据库后删除缓存。
- 延迟双删减少并发下旧值回写。
- 设置 TTL 兜底。
- 对热点数据做主动刷新或失效。

**推荐回答：**

### Q26：多轮会话记忆怎么理解？

**推荐回答：**

大模型本身不记得历史对话，每次请求都需要把必要的历史上下文传给模型。多轮会话记忆就是保存用户之前的问题和模型回答，在下一次请求时按一定策略拼接进 Prompt。

需要注意上下文窗口限制，不能无限追加历史。常见策略有：

- 只保留最近 N 轮。
- 对历史做摘要。
- 重要信息持久化。
- 检索相关历史再注入。

---

### Q27：工具调用和 Web Search 有什么意义？

**推荐回答：**

大模型自身知识可能过时，尤其是技术版本、框架更新、最新博客等内容。通过工具调用或 Web Search，可以让模型在回答前获取外部实时信息，再基于检索结果回答。

在项目里，网页抓取和搜索能力可以用于获取较新的技术资料，增强技术问答的时效性。

**追问：有什么风险？**

- 外部网页质量不稳定。
- 搜索结果可能不准确。
- 抓取内容可能包含广告或噪声。
- 需要做来源筛选、内容清洗和安全过滤。

---

### Q28：安全围栏怎么做？

**推荐回答：**

安全围栏可以分输入和输出两侧。

输入侧：

- 敏感词过滤。
- 恶意 prompt 注入识别。
- 超长输入截断。
- 高频请求限流。

输出侧：

- 敏感内容检测。
- 对危险建议进行拦截。
- 对技术问答中的不确定内容加提示。
- 避免返回违规或误导性内容。

对于学习类助手，尤其要避免输出危险命令、违法内容或明显错误的技术建议。
